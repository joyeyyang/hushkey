# Hushkey（HSK）待辦與現況

每一項都寫「怎麼驗的」，沒驗過的不標完成。

## 1. 輔助使用權限：開關是開的，App 卻說沒有（2026-10-25）

**症狀**：系統設定裡 `OfflineVoiceAssistant` 的開關看起來是開的，
App 仍然顯示「尚未取得輔助使用權限」、貼不出去。

**實際原因（已查證）**：使用者的 TCC 資料庫裡**沒有**
這支 App 的 `kTCCServiceAccessibility` 紀錄，只有麥克風、行事曆、
文件夾。也就是那條「開著的列」不是這支程式。

```
$ sqlite3 "$HOME/Library/Application Support/com.apple.TCC/TCC.db" \
    "select service, client, auth_value from access where client like '%com.example%'"
kTCCServiceSystemPolicyDocumentsFolder|com.example.offlinevoiceassistant|2
kTCCServiceMicrophone|com.example.offlinevoiceassistant|2
kTCCServiceCalendar|com.example.offlinevoiceassistant|2
```

授權綁在程式簽章上。每次重打包換掉 `/Applications` 裡的 App，舊紀錄就
對不上執行中的二進位檔，而系統設定不會把那一列自動收掉——就成了
「開關開著、API 說沒有」的死結，而且那個開關按不掉也重開不了。

補充（01:00 查到的時序）：00:28 時資料庫確實沒有輔助使用列，App 也回報未授權；
00:59:33 從 `dist/` 啟動時卻回報 `trusted=true`，代表那時已經有一筆對得上的授權。
也就是「時好時壞」不是偵測程式有問題，是授權紀錄與當下執行的那份 bundle
對得上或對不上。這批修正把「對不上」的情況變成使用者按一下就能清掉。

**已做**：

- `TextInjector.resetAccessibility()`：跑 `tccutil reset Accessibility <bundle id>`，
  把對不上的舊紀錄清掉。系統設定裡「重設權限（清掉舊紀錄）」按鈕就是它。
- `TextInjector.identity`：`ova.log` 現在會寫出「哪一個 bundle、bundle id、
  當下判定」，下次再發生可以直接看出是不是拿到別的副本。
- 重設後立刻重新呼叫 `AXIsProcessTrustedWithOptions(prompt: true)`，
  這是唯一會讓 App 用「現在的簽章」重新出現在清單裡的正規做法。
- 打包腳本簽完章後跑 `lsregister -f`，避免 LaunchServices 留著舊的 bundle 紀錄。
- 既有的 2 秒輪詢 + 回到前景時重查照舊，授權一到手橫幅會自己消失，不必重開 App。
- 實測 `tccutil reset` 回了 3 次 `Successfully reset`（代表先前真的有 3 筆
  對不上的紀錄），清完後資料庫已無輔助使用列。

**目前狀態**：舊紀錄已清空（`tccutil reset` 回了 3 次成功），資料庫現在沒有
輔助使用列，App 顯示未授權——這是預期中的乾淨起點。

**還要你做一次**：App 開著 → 按橫幅上的「重設權限（清掉舊紀錄）」（或直接用
啟動時跳出的系統對話框）→
系統跳出的對話框按「打開系統設定」→ 在輔助使用清單用「＋」加入
`/Applications/OfflineVoiceAssistant.app` 並打開開關 → 回 App，橫幅應該
在 2 秒內自己消失。

**驗證方式**：`ova.log` 出現 `accessibility trusted: true`，且
`tccutil reset` 之後資料庫出現 `kTCCServiceAccessibility|com.example.offlinevoiceassistant|2`。

## 6.5 AI 整理的三個缺陷（2026-10-25）

使用者回報三件事，都在整理階段（`rust/core_engine/src/llm.rs`）：

1. **口頭指令沒被執行。** 講「把前面那句刪掉」「第二點不要」，結果裡那句還在。
2. **語言被翻走又沒翻回。** 中文問句裡夾了英文產品名，整段變成英文。
3. **結尾多餘的句號。**

**修的辦法（範例優先，規則其次）：**

- `REFINE_SYSTEM` 收緊語言規則：**講什麼語言就寫什麼語言**，句中有英文產品名照留、
  問句也一樣；只有明確要求翻譯時才換語言，而且要整段都換。原本的寫法
  「明確要求換成別的語言」是破口——一句夾英文的中文問句會被讀成這種要求。
- `REFINE_EXAMPLES_ZH` 由 2 組加到 5 組，加了「刪除」與「替換」的示範
  （`下週三下午三點半開會，地點在二樓會議室，把地點那句刪掉…` → `下週三下午三點半開會，地點還沒確定`），
  以及一組「整句中文夾英文產品名，維持中文」。英文範例同步補刪除／替換，並把
  四組舊答案結尾的句號拿掉，讓規則和示範一致。
- **翻譯改成兩段確定性流程**：`detect_translation_request` 先在輸入裡找翻譯指令
  （`翻成英文`／`翻成中文`／`translate into english`…，弱的說法如「用英文」還要
  旁邊有「請／幫／把／這句／整理／回答」才算指令，避免把「我用英文寫了一封信」
  誤判），把指令那段從草稿裡切掉，先**用原語言整理**，再**用同一顆已載入的模型**
  翻譯（`translate_in`，只多一次生成、不多一次載入；日韓文不在 `translate_prompt`
  的支援範圍，維持交給模型）。這樣 2B 模型不必自己判斷要不要換語言。
- **格式由程式強制**：`tidy_output` = 去外框引號 → 單行答案去掉項目符號
  （`• 下週三開會` → `下週三開會`，兩行以上的清單保留）→ 折疊 3 行以上空白 →
  **只砍最後一個** `。`／`.`／`．`（`…`、`？`、`！`、`：`、`；` 和句中的句號不動）。
  摘要輸出不走這一段（摘要是一份文件，項目符號本來就可能以句號結尾）。

**實測**（`Qwen3.5-2B-Q4_K_M`，`ovc-llm-worker refine`）：

| 輸入 | 輸出 |
|---|---|
| 先確認規格。再去找供應商。把前面那句刪掉 | 再去找供應商 |
| 第一，確認規格。第二，找供應商。第三，排時程。第二點不要 | 第一，確認規格。第二，排時程 |
| 呃就是那個，下週三…地點那句先刪掉，我還沒確定 | 下週三下午三點半開會，地點還沒確定 |
| 這個 API 的 rate limit 是多少？ | 這個 API 的 rate limit 是多少？ |
| 把這句翻成英文：明天下午三點跟客戶開會 | Meet with the client at 3 PM tomorrow afternoon |
| 明天下午三點開會。 | 明天下午三點開會 |

單元測試 52 項（含新增的 `strip_lone_bullet`、`detect_translation_request` 純函式測資）。

## 6.6 檢索輔助（EmbeddingGemma INT4）＋語音輸入打包（2026-10-25）

### 模型
`rag-embeddinggemma-300m-q4`：`embedding/embeddinggemma-300m-Q4_0.gguf`，277,852,192 bytes，
sha256 `edc6015cb15694c27be7d1d33f1bc015db9a358ff51ed524628c027504907ba9`。
這是 **QAT（量化感知訓練）的 Q4_0**，不是普通 Q4：MTEB 多語言平均 60.62 對 Q8 的 60.93
（差 0.31），繁中檢索在 5 億參數以下的開源模型裡排名第一（DRCD Hit@5 94.96%）。
架構 `gemma-embedding`，768 維，2048 ctx，**Mean pooling**（不是 Last）。
上游 GGUF 少了 Sentence-Transformers 的 dense module，對本用途沒差：詞與逐字稿都用
同一顆模型算，排名自洽。

### 實測（`rust/core_engine/examples/embed_probe.rs`，全部是真實繁中句子）
**詞彙檢索——排序可靠，門檻不可靠。** 草稿「明天下午三點要跟小林開會，討論隼的第四季
時程，Figma 的稿子我會先更新」：該抓到的 0.402–0.465（小林／隼／第四季／Figma），
不該抓到的 0.260–0.479（`小林設計` 0.479 甚至比 `小林` 0.465 高，因為它真的共用「小林」）。
→ 所以門檻只設 0.35 砍掉明顯無關的尾巴，真正的價值在**排序**與 top-12，不做硬切。

**指令篩選——單一相似度門檻做不到。** 兩次量測間隙都是負的：一般說話
`順序是這樣沒錯` 0.783 ＞ 真指令 `第二點不要` 0.765；`他說時間會改` 0.648、
`我要加薪` 0.628。短句中文 embedding 的相似度主要反映語氣與虛詞，不是意圖。
→ 改成**「關鍵字必須命中」＋「相似度 0.65 確認」**：關鍵字表決定召回（可擴充），
門檻決定精確度（寧漏不錯殺，因為漏掉的指令整理提示詞本身還是會照做）。
保留樣本（未放進範例表的真指令）靠這條規則通過 4/4，帶關鍵字的一般說話誤判 0 筆。

**ASR 沒有標點，這是第一版真正的破口。** 實機聽寫整段是一個超長子句，被長度上限丟掉，
篩選等於完全沒作用（而手寫測試全過）。改成在關鍵字附近取 24 字內的**視窗**；而視窗
**只算分、不注入**——實測把 `季時程把地點那句拿掉我還沒確定另外稿我會` 這種錯位片段
餵給模型，它會認不出來並把指令留成內容；只有完整的短句才引用給模型。

### 架構
- `rust/core_engine/src/embed.rs`：載入、Mean pooling 向量、L2 正規化、詞向量磁碟快取
  （`models/.cache/term-vectors.tsv`，含範例向量，以 model 檔名＋維度驗證；範例用
  `\u{1}` 命名空間與詞彙分開，因為兩者前綴不同）、關鍵字排序、指令篩選、視窗切句。
- `rust/core_engine/src/state.rs`：`screened_hint()` 在整理前把提示詞換成「這次真的講到的詞」，
  並附上「使用者的修改要求（原話）」；`warm_retrieval()` 供主程式先算好向量。
- C ABI：`LLM_RelevantTerms`／`LLM_EditClauses`／`LLM_WarmRetrieval`（沒有模型時回空字串，
  不是錯誤）。`OVC_EMBED_DISABLE=1` 可停用，`OVC_EMBED_MODEL` 可換檔名。
- 設定頁新增「檢索輔助」開關（預設開，`settings.retrieval`）；模型管理頁多一個
  「檢索模型（向量）」分類。

### 效能（M1 8GB，實測）
- 冷快取取暖：29 個向量 2.9 秒；再取暖 0 個（快取有效）。
- 完整聽寫（ASR＋檢索＋LLM 整理）：**6.5–7.4 秒**，幾乎等於基準線（ASR＋LLM）7.5 秒，
  也就是檢索現在幾乎不用錢。
  對照：**檢索放在 App 行程時是 11.8–13.2 秒**，而且 `n_ctx` 從 2048 降到 256 完全沒差
  → 那 4–5 秒不是算向量、也不是 context 配置，是**記憶體壓力**（App 行程同時持有 ASR
  與 277 MB 向量模型，再開 1.2 GB 的 LLM 子行程）。
  **修法：把檢索搬進 worker 行程**（`state::screen_hint_for_worker`）——worker 先載入
  向量模型篩選、放掉它，再載入 LLM，高峰從「相加」變成「取大值」。
  過程中撞到一個真 bug：`embed` 與 `llm` 各自有一個 `OnceLock` 包住
  `LlamaBackend::init()`，以前兩者永遠在不同行程所以沒事，同一個行程就
  `BackendAlreadyInitialized` 讓整個 refine 失敗（退回原文）。改成共用 `llm::backend()`。
- `voiceinput --warm` 可在安裝後／啟動時先把向量算好，避開第一次的延遲。

### 語音輸入打包成可呼叫模組（使用者要求「放在另外一個資料夾」）
`mac/macos_app/Sources/VoiceInputKit/`：獨立 target，含 `VoiceInputConfig`、
`VoiceInputEngine`（`prepare`／`transcribe(fileAt:)`／`makeSession`／`warmRetrievalCache`）、
`VoiceInputSession`（即時錄音）、`relevantTerms(for:in:)`、`editInstructions(in:config:)`、
`CursorInserter`（貼到游標）。另有命令列工具 `voiceinput`：
`--transcribe`／`--raw`／`--selftest`／`--warm`／`--keyword`／`--worker`。
**App 已經改用這個模組**：`OfflineVoiceAssistant` target 依賴 `VoiceInputKit`，
`AppController.polish()` 改成呼叫 `refineTranscript(_:config:)`，App 自己那份
「整理＋檢查＋翻譯」實作刪掉了（`translateIfNeeded` 移除），所以整理鏈只有一份實作，
App 與命令列工具不可能各自漂移。Kit 也已經有系統音訊能力（`VoiceInputKit/SystemAudioCapture.swift`，Core Audio process
tap、macOS 14.2+、與麥克風分開的權限），`VoiceInputConfig.captureSystemAudio` 打開後
逐字稿會自動分成麥克風（我）與系統音訊（對方）兩路，暫停時兩路一起停。
**App 的會議模式仍走原本自己的 tap**：會議要的是原始逐字稿＋摘要（不是整段潤飾），
而 `session.finish()` 會跑整理鏈，所以把會議搬過去需要一個「不潤飾」的 session 模式，
這件事沒做完，我沒有假裝它做完了。

### 錄音視窗合併（使用者要求「麥克風視窗與文字視窗合併」）
`HUDWindow` 改名 `DictationWindow`，`TranscriptWindow.swift` 刪除。現在語音輸入期間只有
**一個**浮動視窗：上方控制列（麥克風、波形、字數、暫停、停止、拖曳點），下方標題列
（狀態膠囊、複製、Esc 關閉）與逐字稿卡片（我：／對方：）。視窗由 56pt 長到 274pt，
逐字稿過長時自己捲動，錨定左上角所以停止鍵不會移動。Escape 仍然只關視窗、不停止錄音。

### 8.4 語音編輯（`LLM_EditText`）

worker 新任務 `edit`：core 自己編號（多行或多句），提示詞要求保留原編號只改被指到的行，
程式依編號解析回來。Kit 加 `isVoiceEditInstruction`／`applyVoiceEdit`；App 把指令套用到
上次交付的文字，再用 Accessibility 精準選取後貼上覆蓋，無法證明位置時只放剪貼簿＋提示。

**實測中發現並修掉的問題**（每個都是真的會咬人的）：

1. **一般句子被誤判成指令，整段吞掉。**「第一點要改善」有「改」也有「第一點」，
   於是被當成編輯指令，使用者的整句話消失不見。修法：裸「改」字要求命令框架
   （把／請／幫／將／給我），而且**編輯失敗時改為直接輸入你講的原話**——
   寧可多貼一句話，不可吞掉整段。CLI 的 `--is-edit` 可重跑這幾個樣本。
2. **單行口語草稿沒有句號**（記錄裡 79% 是這種），「第二句」等於指向不存在的行。
   修法：先按逗號斷句編號，再送模型。
3. **模型的回覆格式不穩。** 同一個提示詞，有時回編號、有時回純文字，而且會隨
   記憶體壓力改變（8 GB 機器上 Metal 數值不穩）。修法：兩種都收，但用行數守門——
   編號的回覆才允許少行（少的那幾行就是刪掉的），純文字的回覆行數必須完全對上，
   否則拒絕（不覆蓋使用者的文字）。
4. **模型把改過的單行重新併回一行。** 這時沒有行數可比，改用**內容保留率**
   （自己原本的字至少保留一半）判斷，並拒絕「只是其中一句」的片段。
5. **貼上前先把結果放剪貼簿**，失敗訊息才不會說謊；只有確認取代成功才更新
   「上次交付的文字」。

### 8.4.1 語音編輯：模型找不到該改哪一行（2026-10-25 傍晚）

前一節的「能用」是在**三行草稿、位置式指令**下量到的。把量測擴大到
內容式指令（「把地點改成三樓會議室」），發現真正的問題不在解析，而在
**模型選錯行**。

用 `rust/core_engine/examples/edit_batch.rs`（一次載入模型、跑一組案例）量測，
三行草稿「明天下午三點跟小林開會，討論第四季時程，地點還沒確定」：

| 指令 | 整份草稿提示詞的結果 |
|---|---|
| 把小林改成大衛 | ✅ 改對 |
| 把三點改成四點 | ✅ 改對 |
| 把第二點改成禮拜五 | ✅ 改對 |
| 把地點改成三樓會議室 | ❌ 沒改 |
| 把時程改成禮拜五 | ❌ 沒改 |
| 把第三點改成三樓會議室 | ❌ 沒改 |
| 把第一句改成大衛拜訪 | ❌ 改錯行 |

**3/7。** 逐項追下去，每一個失敗都有原因，而且不是同一個原因：

* **「把第三點改成…」整段不動。** 範例裡三個位置式案例，改的都是第 2 行，
  刪的是第 3 行——模型學到「最後一行不動」。把範例的位置換掉（改第 3 行、
  刪第 2 行）之後才會改動。
* **「把地點改成…」改到錯的行或不改。** 範例的內容式案例把內容放在**中間行**，
  模型學到「內容式 → 中間行」；換到最後一行後，「把地點改成三樓會議室」對了，
  但「把時程改成禮拜五」變成沒改。
* **範例答案的語意會被學走。** 第一版的內容式範例答案是「討論第四季禮拜五」
  （語意不通），模型照著學，於是內容式指令一律回讀原文。改成語意自然的答案
  才會動。
* **「把三點改成四點」改到了錯的子句。** 「三點」被讀成**位置**（第 3 點），
  而不是「下午三點」這個時間——「三」後面跟「點」就當位置。修法：中文位置詞
  必須有「第」前綴（「第三點」），沒有就是時間。

這些都是提示詞的形狀問題，**但繼續修提示詞修不動**：範例只要有形狀，
模型就會照抄形狀；把範例的形狀打散到每一種可能，又會讓每一種都變差。

### 8.4.2 改成「程式定位 + 模型改寫」

最後的做法是把兩件事分開：**哪一行**由程式決定（算術，不是理解），
**怎麼寫**才交給模型。

* **位置式**（「把第二點改成禮拜五」）：程式讀出位置，**整行直接換成新值**。
  不問模型——這是取代，不是改寫。
* **內容式**（「把地點改成三樓會議室」）：程式找出含那個詞的行，
  **短詞（≤4 字、單一詞）直接字串取代**，長詞（「第四季時程」）才問模型
  改寫整個子句。
* **刪除**：程式直接刪掉那一行。
* **跨行重複的詞**（「把三點改成四點」而「三點」在兩行）：**拒絕**。
  該改哪一行不可判定，整份草稿提示詞也會猜錯（量測：它猜第三行）。
  拒絕是無害的那一邊——使用者保留原本的文字。

量測（同一組三行草稿，8 個案例）**8/8 全部改到正確的行**，且保留原有的標點。

保留的路徑：整份草稿提示詞仍留著，當程式定位不到時（指令完全沒說目標）
才會走那條路。

還修掉三個附帶的 bug：

* **草稿已經有編號時會編號兩次**（「1. 1. 先確認規格」）。修法：編號前先
  去掉既有的編號。
* **改寫後尾部的逗號不見了**。子句靠逗號分隔，改寫丟了逗號，子句就黏在一起。
  修法：把原行的結尾標點放回改寫後的行。
* **單行改寫時模型把新值「前置」**（「大衛明天下午三點跟小林開會」）。修法：
  內容式改寫的提示詞改成「把這行裡的『小林』改成大衛，其他字不變」，
  示範答案也照那個形狀。

### 8.4.3 閘門比核心懂得少（2026-10-25 晚間）

上面的 8/8 量的是**核心**，但 App 不會把每一句話都送進核心——它先問
`isVoiceEditInstruction`「這句話是不是在改東西」，只有答案是 yes 才走編輯。
把同一組指令餵給閘門，才發現**閘門比核心懂得少**：

| 指令 | 閘門 | 核心 |
|---|---|---|
| 把地點改成三樓會議室 | ❌ no | ✅ 改對 |
| 把小林改成大衛 | ❌ no | ✅ 改對 |
| 把三點改成四點 | ❌ no | ✅ 改對 |
| 第二句改短一點 | ❌ no | ✅ 改對（8.4.4） |

也就是說 **8.4.2 的修法從 App 完全走不到**：核心已經會做，閘門卻不放行。
閘門是 Swift 裡獨立寫的一份，只認得「位置」，不認得「內容詞」。

修法有兩面。

**閘門要認得核心認得的東西。** 內容詞（把地點改成…）與相對位置
（最後一句、前面那行）都算目標。

**但閘門不能照抄核心那麼寬。** 核心認得「顏色改成藍色」是因為它在草稿裡
找不到「顏色」——找不到就不是目標。閘門看不到草稿，只能靠句子本身：所以
內容詞必須帶**命令框架**（把／將／請…），而且框架要在**句首**。

* 「把地點改成三樓會議室」→ 開頭是「把」→ 是命令 ✅
* 「我把檔案刪掉了」→ 開頭是「我」→ 是陳述 ❌
* 「顏色改成藍色」→ 沒有框架 → 是陳述 ❌
* 「這個會議改成線上開」→ 沒有框架 → 是陳述 ❌

閘門放寬後，三句日常話確實被誤判成編輯（量到的），加框架規則後全部回到
no，而 11 個真的編輯指令全部 yes。閘門的樣本現在是**測試**
（`mac/macos_app/Tests/VoiceInputKitTests/VoiceEditInstructionTests.swift`），
不再只是註解裡列的樣本。

### 8.4.4 「改短」不是「改成」（2026-10-25 晚間）

閘門放寬後，「第二句改短一點」進來了，卻得到「短一點」——整行被換成這三個字。

原因是核心把「改」當成取值動詞：「改」後面的「短一點」被讀成**新值**，
於是位置式分支把整行換成新值。但「改短」是**變換**（把這行改短），
不是**取代**（把這行換成某值）。變換沒有新值，要的是模型重寫整行。

* 修法：變換動詞（改短／改長／改多／改少／改小／改大／改簡／改複／縮短／
  精簡）不取值，改走模型重寫；提示詞也分開，不再說「把這行完全改成短一點」。
* **「把最後一句改短一點」整句不動**：核心的位置解析只認「第N＋量詞」，
  認不出「最後一句」。修法：加相對位置（最後一句／前面一句／第一句），
  需要行數才能解析，所以放在位置解析器裡。

### 8.4.4.1 編輯探針量的是模型，不是產品（2026-10-26）

清點「語音編輯」的驗證時，發現 `rust/core_engine/examples/edit_batch.rs` 有問題：
它直接呼叫 `llm::generate(&llm::edit_prompt(...))`，量的是**模型原始回覆**。

但模型的回覆是**編號清單**：

```
1. 明天下午三點跟小林開會， | 2. 討論第四季時程， | 3. 地點還沒確定
```

而產品（`state::edit_text` → worker 的 `edit` 任務）要做的事是：**找出指令
指到的那一行、只改那一行、再把草稿原本的形狀放回去**。量模型等於量使用者
永遠不會看到的東西。

而且舊探針的「有沒有改」判定是壞的：它把編號去掉、把各行**接起來**再跟草稿
比。接起來之後那個字串跟草稿幾乎一樣，於是判定「沒改」——量到 **6/11**，
而產品實際上是 11/11。

修法：探針改走 `state::edit_text`（App、Kit、CLI 走的那條路），並且接受
**三欄**的案例檔（指令／草稿／預期答案），逐案比對答案而不只是比對「有沒有變」。

修完：

```
=== 11/11 changed
=== 11/11 right
```

每一案的答案都跟文件裡的表一模一樣，包括最容易被搞錯的三個：

| 指令 | 答案 |
|---|---|
| 把最後一句改短一點 | …，地點未確定（不是「還沒確定」） |
| 把三點改成四點 | 明天下午**四點**跟小林開會（第一句，不是第二句） |
| 把時程改成禮拜五 | …討論第四季**禮拜五**，地點還沒確定 |

過程中還撞到兩個探針自己的 bug：TSV 用 `split_once('\t')` 會把第二欄之後的
內容（含預期答案）黏進草稿；以及三欄檔的欄位切錯。這兩個都讓判定失真而
不是讓它失敗——跟 8.4.8.2 的教訓一樣。

`tests/edit_expected.tsv` 是那 11 案（現在是永久檔案，不再是臨時的），
`scripts/verify.sh` 每次都跑它，共 14 項檢查。

### 8.4.4.2 CLI 的會議摘要：Kit 有，CLI 沒有（2026-10-26）

清點「把整套語音輸入方式打包成函式」這條線時，發現 Kit 已經有
`engine.summarize(_:)`（App 的會議路徑在用），但 **CLI 沒有任何一個選項
叫得到它**。命令列只有 `--transcribe`／`--raw`／`--edit`／`--is-edit`。

所以「整套打包成可再調用的函式」在命令列這一格是**空的**：會議摘要這段
只能從 App 裡走。

補上 `--summarize`：逐字稿從 stdin 進，會議段落出來。

```
$ printf '明天下午三點跟小林開會討論第四季時程。小林說下週三之前會給客戶看初稿。我負責週五之前補上第二段的數字。' \
    | voiceinput --summarize
## 摘要
會議定於明天下午三點與小林討論第四季時程，但具體地點尚未確定。小林表示下週三前會向客戶展示初稿，而您則需在週五前完成第二段的數字補全。

## 決議
決定明天下午三點跟小林開會討論第四季時程，地點尚未確定，小林承諾下週三前提供初稿。

## 待辦
- 我：下週五之前補上第二段的數字
- 下週三之前給客戶看初稿
```

三個細節：

* **摘要跟聽寫清理是兩件事，不能共用一條鏈。** 清理要的是「一行、不重複」；
  會議逐字稿走清理會被壓成一句話，然後「誰答應什麼」就沒了。這也是 8.4.6
  修的那個 bug 的同一件事。
* **繁簡要正規化兩次**：進去之前（辨識器輸出簡體，摘要提示詞跟著逐字稿的
  語言走），出來之後（模型可能還是吐簡體）。
* **失敗要報失敗**，不能印出空字串當成摘要——腳本會把空摘要當成真的存進去。
  空 stdin 是 exit 1，worker 壞掉也是 exit 1。

`scripts/verify.sh` 現在多兩個檢查（CLI 的編輯與摘要），共 13 項。

### 8.4.5 取代的位置要測（2026-10-25 晚間）

語音編輯的最後一步是**在別人的輸入框裡**把使用者剛貼上的那段字換掉。
換錯位置是最貴的失敗：使用者改一句話，結果變的是另一句。

找法是「游標之前、最後一次出現的那段字」——游標是「剛才是貼在這裡」的
證明。這個規則之前沒有測試，而且它不能靠 AX 測（要真的 focus 一個輸入框），
所以拆成純文字的搜尋函式放進 Kit（`VoiceText.insertionRange`），
App 呼叫它。

測試涵蓋：同一段字出現兩次時取游標前最後一次、游標之後的副本不算、
找不到就不換（結果留在剪貼簿）、以及**位移是 UTF-16 單位**（輸入框有 emoji
時位置才不會錯）。

### 8.4.6 會議逐字稿被聽寫提示詞改寫（2026-10-25 晚間）

會議模式搬到 Kit 之後，錄音確實走 Kit 的 `VoiceInputSession`、逐字稿確實是
`result.raw`（沒有整理），但**整理還是有跑**——只是結果被丟掉。

`session.finish()` 無論錄音目的都會跑 `Refiner.refine`，那是**聽寫**用的
清理鏈：一行乾淨的句子、內容不多不少。會議逐字稿經過它會被改寫、濃縮，
而會議紀錄「說了什麼」不能被改寫。會議自己的摘要是**另一個提示詞**、另一步
（`engine.summarize`），讀的是原文——這條路本來就對。

所以這不只是浪費，也是錯的。每一次會議都白白付一次完整整理：

| 模式 | worker 收到的任務 | 耗時 |
|---|---|---|
| 聽寫（對照組） | `["refine"]` | 10 秒 |
| 會議 | `[]` | 1 秒 |

修法：`VoiceInputSession.Mode`（`.dictation` / `.meeting`）決定結束時跑不跑
清理鏈。會議跑的是 `Refiner.tidy`——只做繁簡轉換與項目符號一致，**不重寫**。

**驗證方式**：`OVC_SELFTEST_MEETING=<wav>` 跑一個真的會議 session，
worker 被換成一個會記錄任務的 wrapper，所以「整理有沒有跑」是量得出來的。
`OVC_SELFTEST_MEETING_MODE=dictation` 跑**對照組**：同一套 harness、聽寫模式，
必須看到 refine。沒有對照組的話，一個永遠測不到東西的 harness 也會每次 PASS。

順帶補了兩個 Kit 的洞：

* **`VoiceInputSession.start()` 需要麥克風權限**，headless 的檢查會卡在權限
  對話框。改成可以傳入替代音訊來源（`start(audioSource:)`）：走的是真的
  session、真的 ASR、真的 segments，只是不開麥克風。
* **App 的錄音本來就已經在 Kit 上**：`AudioCapture.swift`、
  `SystemAudioTap.swift`、`CoreBridge.swift` 都已刪除，`AudioFileImport.swift`
  剩下的是 App 自己的政策（重試、忙碌guard、中文訊息），解碼與分段在 Kit。

這些檢查散在不同地方（Rust 單元測試、Swift 單元測試、App 自己的自我測試、

### 8.4.8 輔助使用取代：真的測到了（2026-10-26）

前面修的語音編輯，最後一步是**在別人的輸入框裡**把剛貼上去那段字換掉。
這一步要跟 macOS 的輔助使用（Accessibility）講話：找出使用者正在輸入的
欄位、讀出裡面的字、選中剛貼的那一段、蓋掉。

那一段之前**完全沒有測過**。而且一測就發現問題不只是「沒測」。

### 8.4.8.1 貼上本來就走不到自己的視窗

測試一開就失敗：欄位沒有變。追下去發現選取是**對的**
（`editorSel={0,11}` = 整段被選中）、輔助使用也讀得到值，但 Cmd+V 沒進來。

原因是貼上用的是 **CGEvent 丟到系統的 HID tap**：那個事件送給「最前面的
App」，而 **App 不會收到自己送出的合成按鍵事件**。所以貼到別的 App 沒問題
（正常情況就是貼到別人的輸入框），貼到自己的視窗就不會。

修法：**先用回應鏈**（`NSApp.sendAction(#selector(NSText.paste(_:)))`），
不行才退回 CGEvent。回應鏈是精準的——不會貼錯 App——而且是貼到**自己**時
唯一走得通的方式；貼到別的 App 時回應鏈碰不到（本 App 沒有焦點控制項），
CGEvent 接手。

### 8.4.8.2 測試自己也是一個要寫對的程式

這個測試踩到三個坑，每個都讓它**測不到東西**而不是讓它失敗：

* **視窗沒有 key**：一個不是 key 的視窗不會拿走焦點，欄位編輯器就不是焦點
  元素，取代根本沒作用。修法：App 在測試期間要是 `.regular`（附屬 App
  不能成為最前面），而且**在啟動時就設定**——等測試跑起來再要求已經太遲。
* **貼上是事件，不是同步呼叫**：Cmd+V 是丟到系統的事件，要經過 run loop。
  測試在主執行緒上跑，不給 run loop 轉身的話事件永遠不會送達。修法：
  `RunLoop.current.run` 而不是 `sleep`。
* **診斷自己會改變被測的東西**：中途我加了一個「也用 sendAction 貼一次」
  的診斷，它**自己**把文字貼進去了，讓本來壞掉的取代看起來是好的。拿掉
  之後壞掉的版本才真的被抓到。

### 8.4.8.3 測試抓得到東西（證明）

斷言也補強過：拒絕取代時，除了「欄位沒變」「結果在剪貼簿」，還要檢查
**它沒有謊報成功**——一個回 `.pasted` 的拒絕會讓使用者以為文字換掉了，
而欄位還是舊的。

兩個故障注入，兩個都被抓到：

| 故意弄壞 | 結果 |
|---|---|
| 找不到那段字時回 `.pasted`（謊報成功） | ❌ FAIL: the refusal reported a paste |
| 選取改成「取第一個出現的」而不是游標前最後一個 | ❌ FAIL: field is "昨天開會，然後今天開會", wanted "今天開會，然後昨天開會" |

第二個正是最貴的錯：**使用者改一句話，結果變的是另一句**。

`scripts/ax_check.sh` 跑這個檢查（要對**已安裝**的 App 跑：輔助使用權限
綁在已簽署的 bundle id 上）。四個案例：

```
ok ax replaces the pasted text
ok ax replaces the last occurrence, not the first
ok ax leaves what the user typed afterwards alone
ok ax refuses when the pasted text is gone (refused, result on the clipboard)
AX SELFTEST PASS
```

### 8.5 ASR 的 VAD：安靜講話被整句丟掉、雜訊被當成人聲（2026-10-25 下午）

使用者回報「辨識比內建差」。用 `scripts/asr_bench.py`（`say` 合成 15 個片段，
三種條件）量測，找到四個真缺陷：

| 缺陷 | 證據 | 修法 |
|---|---|---|
| VAD 門檻是**絕對值**（-35 dBFS），小聲或坐遠就整句消失 | 合成語音 peak 0.05 時，quiet 條件 5 句有 **2 句完全空白**；`ova.log` 同一段連續 16 次「silence warning」 | 門檻改成**相對房間底噪的 SNR**（起音 12×、持續 4×），房間吵自己會抬高 |
| 我前一版把滯後門檻弄反（持續 7e-5 > 起音 5e-5） | 審計抓到 | 修正順序並加測試 |
| 短句（<240 ms，如「好」「OK」）被無聲丟棄 | 審計抓到 | 改成「連續 6 個語音框（180 ms）＋總長 ≥0.4 s」 |
| **雜訊被當成人聲**：純高斯噪音解碼出「我。」 | benchmark 的 noise 案例必須是空的，實測吐 `。` | 見下 |

雜訊那一項是量測出來的，不是猜的。三個候選判準都做過：

* **密度**（語音幀佔比 ≥70%）：雜訊有 55% 的幀過門檻、人聲 85–95%，
  方向對，但門檻一高就把安靜講話也殺掉——實作後安靜講話的分數反而掉了。
* **零穿越率**：**完美分開**。量測 15 個語音片段＋3 個雜訊檔：
  人聲每幀中位 630–1300 次／秒，76–88% 的幀低於 4000；
  雜訊與喀噠聲每幀都是 7500–8033 次／秒，**0%** 低於 4000。
  這是語音處理裡標準的濁音判準，用 4000（摩擦音最高的「s」也在其下）。
* 喀噠聲另外被「連續語音框 ≥6」擋掉：100 ms 的爆音最壞會跨 5 個分析幀
  （起訖各含部分幀），所以門檻要是 5 就會被當成一句話。

最終規則：門檻用 SNR、雜訊用零穿越率、喀噠用連續幀數、噪底用「最近 3 秒裡
**未被判定為語音**的幀的最小值」（不是平均——平均會被講話者的聲音抬高，
等於講話者把自己的聲音擋掉）。

**量測結果**（`python3 scripts/asr_bench.py`，每次都可重跑）：

```
loud  mean 0.951  min 0.884  empty 0/5
quiet mean 0.928  min 0.872  empty 0/5
fast  mean 0.916  min 0.811  empty 0/5
noise (must be empty): ''
```

**剩下的是模型本身的限制**：英文詞會被截短（subagent → sub）、同音字（時程 → 時辰）。
要再往上只能換更大的 ASR 模型，而 8 GB 記憶體是這台機器的硬限制。

### 8.6 App 的重複程式碼收掉

`CoreBridge.swift`（App 自己的 C ABI 包裝）與 `AudioFileImport.swift` 的解碼部分
都和 Kit 重複。刪掉 `CoreBridge.swift`；匯入音檔改走 Kit 的
`VoiceInputEngine.transcribe(fileAt:)`，App 只留重試、退避、忙碌鎖與中文訊息，
拖放輔助搬到 `AudioFileDrop.swift`。結果：App 端少一份 C ABI 包裝，
匯入音檔與錄音走**同一套**解碼與分段程式碼，不會各走各的。


### 8.7 語氣是三套提示詞，不是一個形容詞

「正式一點／輕鬆一點」如果寫成同一段提示詞加一句形容詞，2B 會照著**開頭**那句走：
`REFINE_SYSTEM` 一開頭就是「正式的書面文字」，後面再補「輕鬆一點」只是兩個互相
矛盾的開場，先講的贏。所以三種語氣各自是一套完整提示詞加一套範例，語域說明放
最前面（跟原本的提示詞同一個位置、同一個理由）。

`normal` 沒有從另外兩套重建，原封不動：所有回歸案例與 `docs/` 的量測都是對它做的，
重建就等於偷偷換掉預設行為。`casual` / `formal` 是**單段**——兩段式的第一段是中性
改寫，沒有語域概念，語氣會晚一次改寫才到；所以設定裡的段數只對 normal 有效。

值的傳遞刻意用字串而不是 enum：`casual` / `normal` / `formal` 要穿過 C ABI、worker
的 task 名稱（`refine-casual` / `refine-formal`）與兩邊的設定檔，多一層映射就多一個
打錯字的地方。核心對不認識的值一律當 `normal`（打錯字不能讓人損失一次聽寫）；
命令列反而嚴格，`--tone` 打錯直接失敗，免得量測腳本三次都量到 normal 還以為通過。

### 8.8 guardrail 只有一份，而且不呼叫模型

「模型輸出檢查」原本是 Mac 一份、iOS 一份，靠註解互相提醒要一致。iOS 那份晚了好幾個
月才補上，期間模型對著指令回的廢話被原樣貼出去——兩份「說好要一樣」的規則就是這樣
壞的。規則搬進核心（`rust/core_engine/src/guardrail.rs`，C ABI `LLM_CheckOutput`），
兩邊的 `sanityCheck` 只剩薄包裝。

判斷失敗一律**回退**，不重試：重試要多一次推論（20 秒級），而 2B 對自己答案的判斷力
並不比產生答案好。呼叫端的處理統一成「保留原文」——整理退回逐字稿，語音編輯回
`nil`／`unusableResult`，使用者手上的字不動。

檢查本身是純算術（長度、字集、前綴、保留率），實測 3.86 µs/次，對 20 秒的推論是
0.00002%，所以不需要快取或小模型。`sanityCheck` 拿不到核心結果時 **fail-closed**：
核心壞掉時整理全部退回原文，這個方向比「把碎念貼進客戶的信」便宜。

刻意不檢查行數：哪一行還在是編號解析（`llm::check_edited_shape`）的責任，只有它
知道編號。guardrail 只管「這是不是一段文字」。

### 8.9 鍵盤上的「修改的提示詞」：請求放群組，等待分兩段

鍵盤擴充功能不能跑模型（30–40 MB，模型幾百 MB），所以面板寫請求、App 回答。三個通道
（Darwin notification、`ovc://edit`、App 變 active）都走同一個 handler，進去第一件事是
消費序號——同一個請求被兩條通道送到時，不能跑兩次 20 秒的推論。

等待刻意分成兩段，因為單一逾時分不出兩件事：1.5 秒內沒有 ack＝App 沒在跑（顯示訊息
＋「開啟 Hushkey」按鈕），有 ack 就是「在想」，一路等到 120 秒。ack 在呼叫模型**之前**
寫，否則 20–40 秒的推論會被誤判成「App 沒開」，叫使用者去開一個已經開著的 App。

`e.applied` 是為了 Mode 1：開 App 錄「用說的」會把鍵盤殺掉，答案回來的是新行程，沒有
`seq`、沒有 `lastText`。請求因此帶著 `draft`，而「這個答案已經貼過」也必須留在 group，
否則使用者切回來只看到原本的字，而且沒有任何已改好的跡象。

擴充功能叫不出系統鍵盤，所以面板的輸入框只有硬體鍵盤能用；手機上的提示詞用「用說的」
取得，填回同一個輸入框，使用者確認後才「套用」。改完的字只在游標緊接原文時原地替換，
否則放剪貼簿——刪錯別人的字比多按一次貼上貴。

實測（模擬器）：ack 0.27 s，答案 40.25 s，`明天下午三點跟小林開會…` →
`明天下午四點跟大衛開會…`。Mode 2 的零跳轉只能真機驗證，見
`docs/evidence/ios-pip-device-checklist.md`。

### 8.10 一輪 P0–P3：幻覺、鍵盤版面、常駐 worker、HUD 送出（2026-10-29）

八個獨立的小題，一次做完。完整說明在 `docs/milestones.md` 的附錄 N，這裡只留
「改了什麼、怎麼驗的」。

J 的數字（debug build，`tests/edit_expected.tsv` 15 題，答案逐字相同）：

```
一次性 spawn + CPU   15 題 15 次載入   23.1 秒
常駐 + CPU           15 題  1 次載入   23.1 秒
常駐 + Metal         15 題  1 次載入   13.2 秒
```

三個取捨寫在這裡，免得下次有人以為是漏掉的：

1. **`verify.sh` 固定 `OVC_LLM_GPU_LAYERS=0`**。那些檢查比對精確字串，期望值是在
   CPU 上量的；Metal 的累加順序可以讓 greedy 的答案差一個 token。App 仍然走 GPU。
2. **常駐 worker 閒置 300 秒收工**（`OVC_LLM_IDLE_SECS`，`0` = 不收工）。夠長到
   「暫停一下再講」不用重載，夠短到忘了關的 worker 不會握著 1 GB 一整個下午。
3. **iOS 錄音開始就預熱**，代表錄音時多 1.3 GB 的權重。離開前景與記憶體警告會
   立刻釋放，所以代價只在「正在錄音」這段時間。
